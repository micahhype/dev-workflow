# Project map

*What EXISTS in this project and WHERE — the map agents read before proposing to
build something. `conventions.md` says how to write code here; this file says what
is already written. Keep the two apart: a rule goes there, a location goes here.*

**Rules for this file** — these stay; whoever edits the map follows them.
- **Entries are pointers, one to three lines.** Say where a thing lives and what it
  is for; do not restate what the code says. Delete an entry the moment it stops
  being true — agents trust this file, so a stale map is worse than no map.
- **Every entry carries the path it is about**: at the start of the line in the
  list sections (`src/api/` — ...), in the path column of the tables. The map is
  used per module, so one grep for a path must return its rows, building blocks,
  extension points and gotchas together.
- **`Existing features` has one row per CAPABILITY** ("auth", "billing export"),
  not per shipped change. A feature that extends a capability updates its row; only
  a new capability adds one; a bug fix adds none. `Verified` is the date the row was
  last checked against the code — an old date is a row to re-check before trusting.
- **Budget: about 200 lines.** The orchestrator reads the whole file at the start of
  every feature. Past the budget, merge or delete entries before adding one. What
  shipped when is `git log`'s job.

> Generated by `/dev-workflow:init` and kept current by `/dev-workflow:feature`,
> which updates it at every feature's final checkpoint. Re-run `init` to re-derive
> it after a big refactor. It is read LAZILY, unlike `conventions.md`: the
> orchestrator reads it when researching and planning, and hands the coder the
> entries for the modules it is touching.
>
> Delete the guidance blockquotes (this one and the ones under each heading) once
> filled. The rules above are not guidance; keep them.

## Shared building blocks
> The things a new feature is expected to REUSE — base classes, middleware,
> validators, error types, the HTTP/DB client, auth helpers, test fixtures,
> config access. Name the file and when to use it. This section is what stops
> agents writing a fourth retry helper.

## Extension points
> The seams to hook into when adding something: how a route/command/handler/job
> gets registered, where a migration goes, how a new config key is declared, how a
> feature flag is added. "`Y` — to add X" — one line each.

## Known gotchas
> Traps that are not visible from the code being edited: a module that must be
> imported in a certain order, a cache that must be invalidated with a write, a
> table two services both write to, a test that only passes with a fixture loaded.
> Each line should have burned someone at least once.

## Glossary
> Domain term -> what it is called in the code, where they differ (e.g. "top-up"
> -> `WalletCredit`). Skip if the names match.
